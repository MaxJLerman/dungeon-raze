## 2. High-level multiplayer: what is built in, what is missing, add-ons, listen servers, dedicated servers

### Takeaway
Godot's built-in multiplayer gives a transport-agnostic session (ENet, WebSocket, WebRTC, or a plug-in peer such as Steam), RPCs with an authority model, and two replication nodes (MultiplayerSpawner, MultiplayerSynchronizer). A player-hosted listen server for 4 to 5 players is the documented default pattern and is straightforward. Client-side prediction, reconciliation, rollback, lag compensation and network interpolation are not in the engine; netfox (MIT, GDScript) is the one actively maintained add-on that supplies them, with caveats that matter for a melee action game.

### Cited Findings
- Every node has a `multiplayer` property; the server's peer ID is always 1; signals `peer_connected` and `peer_disconnected` fire on all peers. Built-in peers: `ENetMultiplayerPeer`, `WebSocketMultiplayerPeer`, `WebRTCMultiplayerPeer`; custom peers can wrap console or platform APIs. — [High-level multiplayer, Godot 4.7 docs](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html)
- `@rpc` defaults to `("authority", "call_remote", "reliable", 0)`. Modes: `authority` or `any_peer`; `call_local` also runs the call on the sender, which the docs say is needed when the server is also a player; transfer modes `unreliable`, `unreliable_ordered`, `reliable`; numbered channels. RPCs cannot serialise Objects or Callables, sender and receiver need the same NodePath, and every `@rpc` must be declared on both sides. — [High-level multiplayer](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html)
- Hosting is `create_server(PORT, MAX_CLIENTS)` and joining is `create_client(IP, PORT)` on an `ENetMultiplayerPeer` assigned to `multiplayer.multiplayer_peer`. The docs' own lobby example has the host as a player. For internet play with plain ENet "you must forward the port in UDP"; the page offers no NAT traversal. — [High-level multiplayer](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html)
- The docs recommend "server-authoritative logic for gameplay-critical decisions", sending input or intent instead of positions, and note the trade-off of "the need for client-side prediction", which the page does not provide. — [High-level multiplayer](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html)
- MultiplayerSpawner "automates the process of replicating dynamically instantiated nodes across peers", including for players who join mid-game; MultiplayerSynchronizer replicates chosen properties from the node's authority. The recommended pattern keeps the character's authority on the server and gives the owning peer authority over a separate input node. `change_scene_to_*` mid-session is a known problem; the spawner is the workaround. The article (February 2023) says nothing about prediction, interpolation or lag compensation. — [Multiplayer in Godot 4.0: Scene Replication](https://godotengine.org/article/multiplayer-in-godot-4-0-scene-replication/)
- An independent comparison (Rivet, September 2023, updated February 2024; a vendor) lists what is missing against Unity's Fish-Net: "No client-side prediction, lag compensation, predicted spawning, or prioritization"; send rates per node, not per property or peer; complex types need hand-written encoding; sporadic disconnects above about 40 concurrent users in its test; 66 open networking bugs at the time. It calls Godot's replication good for "hobbyist multiplayer games" and "buggy and still very young". — [Rivet: Is Godot 4's Multiplayer a Worthy Alternative to Unity?](https://rivet.dev/blog/godot-multiplayer-compared-to-unity/)
- Forum threads in 2026 still report MultiplayerSynchronizer confusion: synchronizer visibility not stopping the spawner from spawning (Godot 4.6), and properties silently not syncing. — [Godot forum thread on visibility](https://forum.godotengine.org/t/multiplayersynchonizer-visibility-does-not-affect-spawner/137629); [Godot forum: not syncing, no errors](https://forum.godotengine.org/t/multiplayersynchronizer-not-syncing-properties-no-errors/141965)
- **netfox**: MIT, GDScript, "Godot 4.x is supported". Features: shared network time, client-server architecture, interpolation, "Lag compensation with Client-side Prediction and Server-side Reconciliation", and NAT punch-through and relay through its `noray` server. Packages: netfox (core), netfox.noray, netfox.extras (input base classes, weapons, rewindable state machine), netfox.internals. About 1,130 stars, 360 commits; last push 11 November 2026. C# support is "experimental" through a separate NetfoxSharp repository (27 stars, last push December 2025). — [netfox on GitHub](https://github.com/foxssake/netfox); [NetfoxSharp](https://github.com/CyFurStudios/NetfoxSharp)
- netfox's latest tagged release is v1.35.3, dated 23 November 2025: physics rollback (contributed), a built-in latency and packet-loss simulator, inputless RollbackSynchronizer for NPCs and bots, reduced bandwidth, per-peer visibility filtering. Earlier: v1.25.3 (March 2025, input delay, experimental rewindable actions), v1.19.1 (December 2024, hitscan weapons, input prediction, rollback debugger). — [netfox releases](https://github.com/foxssake/netfox/releases)
- How netfox rollback works: the server "rewinds its time and resimulates the whole game from the time of the new input"; clients rewind to the last server state and resimulate; nodes implement `_rollback_tick`; a history limit trades memory for tolerated latency; input redundancy and optional input delay are built in. — [netfox: NetworkRollback guide](https://foxssake.github.io/netfox/latest/netfox/guides/network-rollback/)
- netfox's documented caveats: `move_and_slide()` assumes the engine's delta, so velocity must be multiplied by `NetworkTime.physics_factor`; `is_on_floor()` is stale during rollback and needs a zero-velocity move first; "Rollback and physics-based games (RigidBodies) don't work at the moment" in core (an optional physics add-on exists in netfox.extras); physics queries such as `intersect_shape()` can misbehave because physics does not step between rollback ticks; ordinary state machines break under re-simulation, so `RewindableStateMachine` must be used. — [netfox: Rollback caveats](https://foxssake.github.io/netfox/latest/netfox/tutorials/rollback-caveats/)
- Games listed as made with netfox, all on Steam: Bubble Battle (fighting), PL4no-B (2D tactical shooter), Chrome Carnage (top-down shooter), Nitro Turtles (racing), Kick and Hide (4 to 6 players). — [Made with netfox](https://foxssake.github.io/netfox/latest/made-with-netfox/)
- The netfox public noray instance is for prototyping only: "The instance has configured limits, and no uptime guarantees are made"; a shipping game hosts its own (noray is MIT, 114 stars, last push September 2026). — [netfox on GitHub](https://github.com/foxssake/netfox); [noray](https://github.com/foxssake/noray)
- **Monke-Net**: a C# add-on with CharacterBody client-side prediction and reconciliation, snapshot interpolation and clock sync; lag compensation and delta compression are unticked on its list. It needs its own fork of Godot: "Due to current limitations on Godot Physics and the Jolt module it is impossible to step the physics world manually in vanilla Godot". 250 stars, last push October 2026, no tagged releases. — [Monke-Net on GitHub](https://github.com/grazianobolla/godot-monke-net)
- The engine pull request that would allow manual physics stepping (`PhysicsServer3D::space_step()`, #76462) is still open with the unscheduled 4.x milestone on 20 November 2026. — [godotengine/godot PR 76462](https://github.com/godotengine/godot/pull/76462)
- **Godot Rollback Netcode** (David Snopek): an MIT add-on "for implementing rollback netcode in the Godot game engine", created July 2021, 104 commits, 13 releases. — [godot-rollback-netcode on GitLab](https://gitlab.com/snopek-games/godot-rollback-netcode)
- Dedicated servers: since 4.0 any platform's binary runs headless with `--headless`; an export preset can be set to "Export as dedicated server", which adds the `dedicated_server` feature tag and can strip visuals to placeholders. The docs suggest a systemd service or Docker for hosting. — [Exporting for dedicated servers](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_dedicated_servers.html)
- A 2026 forum discussion (Godot 4.7) on host-authoritative versus dedicated for a Steam game concluded that host-authoritative is the simple start, with the stated concerns being host cheating, the host's upload bandwidth, and that "replaying physics state for late input has no good Godot solution yet". — [Godot forum: Deciding on multiplayer architecture for Steam](https://forum.godotengine.org/t/deciding-on-multiplayer-architecture-for-steam/140817)
- A developer write-up of host-authoritative drop-in co-op in Godot 4.5 (Tumblefire, February 2026): host owns damage, AI and knockback; clients send request RPCs that the host validates and broadcasts; only weapon fire is predicted on the client; 20 Hz for entities near a player and 5 Hz for far ones; Steam relay as primary transport with ENet for LAN and development behind one abstraction. The team cut co-op from four players to two because lag compensation got harder with each player. — [Lost Rabbit Digital dev blog](https://lostrabbitdigital.pages.dev/blog/tumblefire-multiplayer-host-authority.html)

### Inferences
- A listen server for 4 to 5 players is the path of least resistance in Godot: the host is peer 1, runs enemies and combat resolution, and the documented API covers it without add-ons.
- The hard part for this game is responsiveness of a Soulslike on a client: dodge invulnerability frames, parry windows and hit reactions resolved on the host arrive one round trip late. The choices are (a) host-authoritative with each client owning its own character and its own defensive outcomes (dodge, parry, block decided locally, then reported), which is the common co-op compromise and needs no add-on, or (b) netfox prediction and rollback for players. Option (b) is plausible only for the player characters; re-simulating dozens of enemies with AI on every correction is a cost netfox's docs do not quantify.
- DungeonRaze already does its own collision from a 2D scalar field (`world.resolve`, `fieldAt`) and its own hit tests in script. If the rebuild keeps that in script, gameplay does not depend on the physics engine, which avoids the largest netfox and Monke-Net limitation (no manual physics stepping in stock Godot, PR 76462 still open).
- netfox is the only add-on that is both maintained and shipping in released games, but its released games are small shooters, racers and party games. I found no released 3D melee action co-op game on it, and its last tagged release is a year old (November 2025) although commits continue.
- Monke-Net requiring a custom engine fork rules it out for a solo developer who also wants console middleware or easy upgrades.

### Gaps
- I could not confirm whether Godot Rollback Netcode supports Godot 4 or is still maintained; the GitLab page showed no dates. It is designed for deterministic input-synchronised games (fighting games), which this is not.
- No measured data on netfox CPU cost with many rollback-aware nodes, or on bandwidth for about 30 to 60 enemies at 4 to 5 players.
- I found no first-party statement of a maximum practical player count for MultiplayerSynchronizer; the 40-user figure is from one vendor test in 2023.

## 3. Platform services: Steam, Epic Online Services, Nakama, relays and NAT traversal

### Takeaway
On Steam the standard route is GodotSteam, which provides a MultiplayerPeer over Steam Networking Sockets so Godot's RPCs and replication run over Valve's relay with no port forwarding, plus lobbies and invites. It is actively maintained but had a serious peer-identity flaw disclosed in November 2026, fixed in 4.24. Off Steam, the options are Epic Online Services through a community GDExtension, netfox's noray, WebRTC with your own signalling and TURN servers, or a relay you host.

### Cited Findings
- GodotSteam is MIT licensed, for Windows, Linux and macOS, and comes as an engine module, a GDExtension, a server flavour and a MultiplayerPeer flavour. The current build is 4.24; Steamworks SDK 1.65 works with GodotSteam 4.21 or newer; GodotSteam 4.20 changed for compatibility with Godot 4.7. The project moved from GitHub to Codeberg (the GitHub repository was archived on 10 November 2026, with 3,772 stars). — [GodotSteam on Codeberg](https://codeberg.org/godotsteam/godotsteam); [GodotSteam on GitHub (archived)](https://github.com/GodotSteam/GodotSteam)
- GodotSteam release cadence in autumn 2026: v4.23 on 5 October, v4.23.2 on 20 October, v4.24 on 8 November. — [GodotSteam on GitHub (archived)](https://github.com/GodotSteam/GodotSteam)
- Security disclosure (oss-sec, 4 November 2026, Tomasz Kaye): GodotSteam's multiplayer peer "accepts whatever peer ID the sender writes into its first packet and never compares the two", so a client can claim ID 1 (the server) and have the host run authority-gated RPCs; demonstrated on stock Godot 4.7.2 with GodotSteam 4.23.2. Affected: GodotSteam 4.17 (10 December 2025) through 4.23.2 and the older MultiplayerPeer add-on from v4.11-mp. No memory corruption is claimed. — [oss-sec disclosure](https://seclists.org/oss-sec/2026/q4/518)
- GodotSteam 4.24's changelog entry is "Fixed: peer ID claim during setup and bad peer rejection". — [GodotSteam on Codeberg](https://codeberg.org/godotsteam/godotsteam)
- A vulnerability database lists the flaw as CVE-2026-123017, affecting 4.17 through 4.23.2. — [Mend vulnerability database](https://www.mend.io/vulnerability-database/CVE-2026-123017/)
- Steam Datagram Relay: traffic is relayed over Valve's backbone, "IP addresses are never revealed", traffic is "authenticated, encrypted, and rate-limited", and for P2P on Steam "Steam will take care of everything else". For players on other stores the game must also ship on Steam and Valve "cannot promise that this service will always be available to non-Steam players". The page states no price. — [Steamworks: Steam Datagram Relay](https://partner.steamgames.com/doc/features/multiplayer/steamdatagramrelay)
- A separate community peer, `steam-multiplayer-peer` (GDExtension, MIT, 515 stars), last pushed December 2025. — [expressobits/steam-multiplayer-peer](https://github.com/expressobits/steam-multiplayer-peer)
- Epic Online Services: the community plugin EOSG (MIT, GDExtension wrapping the EOS C SDK, Godot 4.2+, usable from GDScript and C#) covers auth, lobbies, sessions, P2P, voice, achievements, stats and leaderboards, on Windows, Linux, macOS, Android and iOS. Web is not listed. Latest release 2.3.1 on 15 September 2026; 328 stars. The README says it is "provided solely for educational purposes" and unaffiliated with Epic. — [epic-online-services-godot](https://github.com/3ddelano/epic-online-services-godot)
- Nakama: Heroic Labs' Godot client SDK is Apache-2.0 with 786 stars; its last tagged release is v3.4.0 from 19 March 2024, though the repository was pushed on 4 November 2026. — [nakama-godot](https://github.com/heroiclabs/nakama-godot)
- Plain ENet over the internet needs UDP port forwarding on the host's router; Godot's docs give no built-in punch-through. — [High-level multiplayer](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html)
- WebRTC in Godot needs a signalling server to exchange session descriptions before peers connect directly; it is built into web exports and needs the `webrtc-native` GDExtension on native platforms (1.2.2-stable, 30 September 2026). — [WebRTC, Godot docs](https://docs.godotengine.org/en/stable/tutorials/networking/webrtc.html); [godotengine/webrtc-native](https://github.com/godotengine/webrtc-native)
- A shipped pattern: a `NetworkBackend` abstraction that picks Steam relay in release builds and ENet for LAN and development. — [Lost Rabbit Digital dev blog](https://lostrabbitdigital.pages.dev/blog/tumblefire-multiplayer-host-authority.html)

### Inferences
- For a Steam release, GodotSteam at 4.24 or later with Steam lobbies and relay is the lowest-cost way to get friends-list invites and NAT traversal for a 4 to 5 player listen server. The November 2026 flaw shows the Steam peer layer is community code that needs its updates tracked, and that host code should validate the sender of every RPC regardless.
- GodotSteam as a GDExtension keeps the stock editor; the module flavour needs GodotSteam's own editor build. The GDExtension route is friendlier to command-line builds and to W4's console builds.
- Steam networking is desktop only. Phones and browsers cannot join a Steam-relay session, so cross-play with mobile or web forces a second transport (EOS P2P on mobile, WebRTC or WebSocket on web) or a dedicated relay.
- EOS in Godot rests on a single-maintainer plugin; it works on mobile, which GodotSteam does not, but carries more risk than Unity's or Unreal's first-party EOS support.

### Gaps
- godotsteam.com refused the automated read (403), so the official feature documentation (lobbies, SDR configuration, list of games using it) was not read; the facts above come from the repository README and release tags.
- Whether the CVE identifier is final: the disclosure on 4 November said an ID had been requested; the CVE number comes from a third-party database, not from MITRE.
- No source confirmed the cost of SDR; Valve's page gives none. It is generally understood to be free for Steam games, but I could not cite that.
- W4 Games' cloud and multiplayer services were not on the page I read; status in 2026 unconfirmed.

## 4. Web export and mobile export in 2026

### Takeaway
Godot 4 exports to the web with the Compatibility (WebGL 2) renderer only, single-threaded by default since 4.3, and without C#: the official 4.7 docs still say C# projects "cannot be exported to the web", and the Foundation said in June 2026 it is "evaluating solutions". A browser build can only be a WebSocket client or a WebRTC peer, so it cannot join an ENet or Steam session. Native Android and iOS export is solid for GDScript; C# on mobile is still labelled experimental.

### Cited Findings
- "Projects written in C# using Godot 4 currently cannot be exported to the web." "Godot 4 can only target WebGL 2.0 (using the Compatibility rendering method)"; Forward+ and Mobile are unsupported and WebGPU is not supported. — [Exporting for the Web, Godot 4.7 docs](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)
- Since 4.3 the single-threaded export is "the preferred and now default way to export your games on the Web" and works on itch.io and on macOS and iOS; threads are optional and need `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp`, without which "the project will not run". — [Exporting for the Web](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)
- "Safari has several issues with WebGL 2.0 support that other browsers don't have"; the docs recommend Chromium or Firefox. On mobile browsers "CPU and GPU performance is at a premium". "The project will be paused by the browser when the tab is no longer the active tab", which can disconnect networked games. — [Exporting for the Web](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)
- Web networking: "Low-level networking is not implemented due to lacking support in browsers." Supported: HTTP client, WebSocket (client) and WebRTC. — [Exporting for the Web](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)
- GDExtensions on web must be compiled for the web platform and "Extensions Support" enabled in the export options. — [Exporting for the Web](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)
- Default web audio since 4.3 is sample playback through Web Audio, which lacks effects, reverb and procedural generation; stream playback has the full feature set at higher latency. — [Exporting for the Web](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)
- WebAssembly SIMD is on by default from 4.5. — [Godot 4.5 release page](https://godotengine.org/releases/4.5/)
- C# web status in the engine repository: the tracking issue "Readd support for web platform exports when using the C# (.NET) version" (#70796, opened January 2023) is still open and was locked on 19 June 2026 by the release manager: "The foundation is evaluating solutions for C# web support." The draft PR "[.NET] Add web export support" (#106125, opened May 2025) is still an open draft on the unscheduled 4.x milestone; several 2026 attempts were closed. — [Issue 70796](https://github.com/godotengine/godot/issues/70796); [PR 106125](https://github.com/godotengine/godot/pull/106125)
- Size: one third-party guide (a competing web-engine vendor, unsourced figures) gives an empty Godot web build as about 5 MB with Brotli and about 9 MB gzipped, against about 7.7 to 10.7 MB for Unity 6. — [Cinevva: Godot vs Unity for Web Games (2026)](https://app.cinevva.com/guides/godot-vs-unity-web-games)

- `WebSocketMultiplayerPeer` supports `create_server(port, bind_address, tls_server_options)` and `create_client(url)` with `ws://` or `wss://`. — [WebSocketMultiplayerPeer class reference](https://docs.godotengine.org/en/stable/classes/class_websocketmultiplayerpeer.html)

### Inferences
- Choosing C# rules out a browser build for the foreseeable future. Choosing GDScript keeps web possible, on the lowest renderer tier.
- Web and native players can share a session only if every peer speaks WebSocket or WebRTC. A native host could run a WebSocket server, but a browser page served over HTTPS can only open `wss://` connections, which needs a TLS certificate and a reachable address for a player's home machine; in practice that means a hosted relay or dedicated server, or WebRTC with hosted signalling and TURN. This is browser policy, not something I found stated in Godot's docs.
- The current game's phone audience plays in a browser, iPhone included. Godot's web export on iOS Safari is the weakest of its targets (documented Safari WebGL 2 issues plus repeated user crash reports tied to memory), so "playable in a phone browser" would likely get worse, not better, than the hand-written WebGL page. Native iOS and Android apps are the realistic route to phones, which adds store accounts and review.
- The owner's Mac satisfies the iOS export requirement.

### Gaps
- No authoritative 2026 statement on iOS Safari stability for 3D Godot web builds; the evidence is forum reports from 2024 to 2025 and the docs' general warning.
- No reliable measurement of web load size or frame rate for a 3D Godot 4.7 game; the only size figures come from a competitor's unsourced guide.
- Whether GDExtensions on web still require cross-origin isolation in 4.7 was stated by the summary of the docs page I read but I did not verify the wording.
- I did not confirm from documentation whether netfox or GodotSteam-free relay add-ons run in web exports.

## 5. 3D capability for a third-person melee action game

### Takeaway
Godot 4.7 has every building block this game needs: AnimationTree with state machines, blend spaces and root motion, call-method animation tracks, a new IK framework, Blender and glTF import, kinematic character bodies, areas for hit and hurt boxes, a navigation server that bakes at run time, GPU particles and three renderers. Its weak points relative to Unity and Unreal are high-end rendering, the size of the asset and tooling ecosystem, first-class networking, and console support, none of which is central to a stylised game in dark caves.

### Cited Findings
- AnimationTree plays clips from an AnimationPlayer and offers Blend2/Blend3, OneShot ("will execute an animation once and return when it finishes", with fade times and filters), TimeScale, TimeSeek, Transition, BlendSpace1D and 2D, and a StateMachine with immediate, sync and at-end transitions, crossfade time and curve, advance conditions and expressions, and `travel()` that pathfinds between states. — [Using AnimationTree, Godot docs](https://docs.godotengine.org/en/stable/tutorials/animation/animation_tree.html)
- Root motion: choose the root bone as the root motion track, then read `get_root_motion_position()`, `get_root_motion_rotation()` each frame and feed it to `move_and_slide` on a CharacterBody3D. — [Using AnimationTree](https://docs.godotengine.org/en/stable/tutorials/animation/animation_tree.html)
- AnimationPlayer track types include "function calling" (call-method tracks). — [Using AnimationTree](https://docs.godotengine.org/en/stable/tutorials/animation/animation_tree.html)
- Animation markers (named sub-regions usable in AnimationTree) arrived in 4.4; bone constraints and aim, copy and convert modifiers in 4.5; the IK framework (TwoBoneIK3D, FABRIK3D, CCDIK3D and others) in 4.6. — [Godot 4.4](https://godotengine.org/releases/4.4/); [Godot 4.5](https://godotengine.org/releases/4.5/); [Godot 4.6](https://godotengine.org/releases/4.6/)
- Import: glTF 2.0 is the recommended format; `.blend` files import directly by calling Blender (3.0 or later must be installed; not available in the Android or web editors); FBX imports through the built-in ufbx library since 4.3. — [Available 3D formats, Godot docs](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/available_formats.html)
- Navigation: `NavigationServer3D.parse_source_geometry_data()` then `bake_from_source_geometry_data_async()` bakes on a background thread; "For runtime (re)baking prefer using physics shapes as parsed source geometry" because visual meshes must be read back from the GPU, "stalling the RenderingServer"; large worlds can be baked in chunks with a baking AABB and border size; a navmesh can also be built directly in script from vertices and polygons. — [Using navigation meshes, Godot docs](https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_using_navigationmeshes.html)
- Renderers: Forward+ is "the most advanced renderer, suited for desktop platforms only"; Mobile runs on mobile and desktop through Vulkan, D3D12 or Metal; Compatibility uses OpenGL and is the only option for web. Lights per mesh: Compatibility 8 omni and 8 spot (raisable); Mobile 8 omni and 8 spot per mesh; Forward+ 512 per cluster. Missing in Mobile: SSAO, SSR, SSIL, volumetric fog, SDFGI, VoxelGI, TAA. Missing in Compatibility in addition: decals, particle trails, particle SDF collision, depth of field, light projectors. — [Renderers, Godot docs](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)
- Rendering work relevant to dark interiors: ubershaders against shader stutter (4.4), lightmap shadowmasks (4.4), specular occlusion (4.5), shader baker (4.5), SSR overhaul and cheaper reflection probes (4.6), area lights (4.7), native Trail3D for weapon trails (4.8 beta). — [Godot 4.4](https://godotengine.org/releases/4.4/); [Godot 4.5](https://godotengine.org/releases/4.5/); [Godot 4.6](https://godotengine.org/releases/4.6/); [Godot 4.7](https://godotengine.org/releases/4.7/); [Godot 4.8 beta 1](https://godotengine.org/article/dev-snapshot-godot-4-8-beta-1/)
- Jolt differences that touch action games: contact reporting between kinematic bodies is opt-in, ray-cast face index is off by default, several joint soft-limit properties are unsupported. — [Using Jolt Physics](https://docs.godotengine.org/en/stable/tutorials/physics/using_jolt_physics.html)
- Third-party behaviour tooling exists: LimboAI (behaviour trees and state machines, MIT, 3,135 stars, pushed October 2026). — [LimboAI on GitHub](https://github.com/limbonaut/limboai)
- Commonly stated weak points, from comparison articles of mixed quality: Godot "isn't as suitable for the kind of high-end, photorealistic 3D environments that Unity and Unreal are known for"; "it still lags behind Unity and Unreal for complex 3D projects"; a smaller asset store, limited console support and fewer third-party libraries; Unreal's replication is built in while Godot's is not. — [GameFromScratch: Godot vs Unity](https://gamefromscratch.com/godot-vs-unity-which-to-choose-in-2025/); [itch.io blog: engine showdown](https://itch.io/blog/1067028/game-engine-showdown-2025-unity-vs-godot-vs-unreal-which-should-you-choose); [Game Design Skills: Is Godot good?](https://gamedesignskills.com/game-design/is-godot-good/)
- A solo developer ported a 3D first-person survival shooter (Road to Vostok) from Unity to Godot 4 in three months and 615 hours, reporting "only minor painpoints". — [80.lv](https://80.lv/articles/this-upcoming-survival-shooter-game-switches-from-unity-to-godot)

### Inferences
- The game's look (primitive-built characters, faceted lighting, dark caves and brick with a few point lights) sits well inside what even the Mobile renderer does. The per-mesh limit of 8 omni lights on Mobile and Compatibility matters for a large merged world mesh: the generated dungeon should be split into chunks (the sewer already has "pieces"), which also gives culling.
- Hit windows map directly onto call-method tracks or onto script timers. The existing game drives attacks from data-table timings (`wind`, `act`, `rec` seconds), which is easier to keep in sync over a network than animation-driven events, so the tables can remain the source of truth with animations fitted to them.
- If characters stay primitive-built, AnimationTree is optional: the current code poses limbs procedurally each frame, and that carries over as node transforms. Moving to rigged characters from Blender is where AnimationTree, root motion and IK start to matter, and it is new content work, not porting.
- Run-time navmesh baking from collision shapes fits seeded dungeons, but the game already has its own grid router (`world.route`), which could be kept and would behave identically on every peer.

### Gaps
- No hands-on benchmark of Godot 4.7 3D performance on phones was found.
- I found no postmortem of a Godot third-person melee action game with lock-on and root motion; the evidence that these systems are production-proven for this genre is thin.
- Camera collision, lock-on and hit-stop are all hand-built in any engine; no ready-made Godot Soulslike kit was evaluated.

## 6. Procedural generation at run time and determinism across peers

### Takeaway
Building meshes and collision in code at run time is a first-class, documented workflow in Godot (ArrayMesh, SurfaceTool), and the existing marching-squares generator maps onto it directly. Determinism across peers should come from the game's own seeded generator ported as written, not from Godot's RandomNumberGenerator, whose algorithm the docs call an implementation detail.

### Cited Findings
- ArrayMesh builds surfaces from arrays in script and is "slightly faster than SurfaceTool"; SurfaceTool has an immediate-mode style API with helpers such as `generate_normals()` and `index()`; MeshDataTool is the slowest; ImmediateMesh suits debug drawing. All run on the CPU. — [Procedural geometry, Godot docs](https://docs.godotengine.org/en/stable/tutorials/3d/procedural_geometry/index.html)
- RandomNumberGenerator "currently uses PCG32" and "The underlying algorithm is an implementation detail and should not be depended upon"; "A given seed will give a reproducible sequence"; "The RNG does not have an avalanche effect, and can output similar random streams given similar seeds". — [RandomNumberGenerator class reference](https://docs.godotengine.org/en/stable/classes/class_randomnumbergenerator.html)
- Navigation meshes can be baked asynchronously at run time from collision shapes or from pure data arrays, and "If the source geometry is pure data arrays, the whole process can run on a background thread". — [Using navigation meshes](https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_using_navigationmeshes.html)
- The 4.6 release adds a tool that generates matching primitive CollisionShape3D nodes from box, sphere, cylinder and capsule meshes, and GridMap painting improvements; 4.7 adds a dedicated MeshLibrary editor; 4.8 adds GridMap octant visualisation. — [Godot 4.6](https://godotengine.org/releases/4.6/); [Godot 4.7](https://godotengine.org/releases/4.7/); [Godot 4.8 beta 1](https://godotengine.org/article/dev-snapshot-godot-4-8-beta-1/)
- Jolt's ConcavePolygonShape3D (triangle-mesh collision) is supported; enabling ray-cast face indices raises its memory by about 25%. — [Using Jolt Physics](https://docs.godotengine.org/en/stable/tutorials/physics/using_jolt_physics.html)
- A developer rejected lockstep for co-op because "Godot does not guarantee deterministic physics across machines". — [Lost Rabbit Digital dev blog](https://lostrabbitdigital.pages.dev/blog/tumblefire-multiplayer-host-authority.html)
- The current generator: `genWorld` and `genSewer` consume one seeded stream in a fixed order, sample a scalar field on a one-unit grid, run marching squares for walls, and are pinned by hash tests of the mesh for fixed seeds (`tests/t22.mjs`). — [Project working notes, local repository CLAUDE.md](file:///Users/maxlerman/Documents/Research/.research/dungeon-raze/CLAUDE.md)

### Inferences
- Each peer can generate the dungeon locally from a seed sent by the host, as long as the generator's RNG is the project's own (ported bit for bit) and layout decisions avoid platform-dependent floating-point paths. The layout graph and field are integer-grid and simple arithmetic, so matching layouts across desktop peers is realistic; a hash of the generated field exchanged at load would detect any mismatch. The existing hash tests are a ready-made cross-platform determinism check.
- Collision for the generated world can be either a trimesh shape built from the same triangles, or no engine collision at all for movement if the field-based `resolve` is kept. Keeping the field as the single truth (the project's own rule that "rubble is only ever a change to the field") is compatible with Godot and with rollback, and makes the host's and clients' collision identical by construction.
- GridMap is a poor fit: the caves are a smooth marching-squares outline, not tiles. ArrayMesh per chunk is the fit.
- JavaScript numbers are 64-bit doubles; GDScript `float` is also 64-bit, while Vector3 components are 32-bit in standard builds (from my own knowledge of the engine, not checked against a source in this session). A port that stores field values in packed float32 arrays or vectors can diverge from the JS hashes; the hashes would need re-baselining, which is acceptable since saved seeds are not player-facing.

### Gaps
- I did not find a Godot documentation page stating cross-platform floating-point guarantees for GDScript, or the cost of building a roughly 80,000-triangle ArrayMesh plus trimesh collider at load on a phone.
- `Mesh.create_trimesh_shape()` and `ConcavePolygonShape3D` run-time use was not read from a docs page in this session; it is standard API but uncited here.

## 7. GDScript versus C# versus GDExtension

### Takeaway
GDScript exports everywhere including web and is the language the engine's docs, add-ons (netfox, GUT) and examples assume; C# is faster and has better static tooling but cannot export to web, is experimental on mobile and in beta on only two consoles; GDExtension (C++ or Rust) is for hot spots. For this game's simulation size, GDScript with typed code is likely sufficient, and it is the only choice that keeps web open.

### Cited Findings
- C#: desktop supported since 4.2; Android and iOS "experimental"; web not possible. — [C#/.NET docs](https://docs.godotengine.org/en/stable/tutorials/scripting/c_sharp/index.html)
- .NET requirements moved from .NET 8 (4.4) to .NET 10 (4.8 beta). — [Godot 4.4](https://godotengine.org/releases/4.4/); [Godot 4.8 beta 1](https://godotengine.org/article/dev-snapshot-godot-4-8-beta-1/)
- C# on consoles through W4 is beta on Switch and Xbox Series only. — [W4 Consoles](https://www.w4games.com/w4consoles)
- Performance, older first-party estimate quoted on the Godot forum: C# "while generally in the same order of magnitude — is roughly ~4× that of GDScript in some naive cases". — [Godot forum: State of GDScript vs C# performance](https://forum.godotengine.org/t/state-of-gdscript-vs-c-performance-in-godot-4-0/5875)
- A C++ scripting vendor's own math stress test claims about 20x over GDScript and 14.5x over C# (biased source). — [Jenova framework benchmark](https://jenova-framework.github.io/docs/pages/Misc/Benchmark)
- GDScript gained typed dictionaries (4.4), abstract classes, variadic functions and release-build backtraces (4.5), and targeted warnings (4.8 beta); a hover documentation and expression evaluator at breakpoints (4.4). — [Godot 4.4](https://godotengine.org/releases/4.4/); [Godot 4.5](https://godotengine.org/releases/4.5/); [Godot 4.8 beta 1](https://godotengine.org/article/dev-snapshot-godot-4-8-beta-1/)
- Rust bindings (godot-rust/gdext, MPL-2.0, 5,412 stars) are at v0.5.5 (August 2026), still pre-1.0. — [godot-rust/gdext](https://github.com/godot-rust/gdext)
- Ecosystem by language: netfox is GDScript with experimental C# through a wrapper; Monke-Net is C# only; gdUnit4 supports both; GUT is GDScript; the EOS plugin is a GDExtension usable from both. — [netfox](https://github.com/foxssake/netfox); [Monke-Net](https://github.com/grazianobolla/godot-monke-net); [gdUnit4](https://github.com/godot-gdunit-labs/gdUnit4); [GUT](https://github.com/bitwes/Gut)
- Slay the Spire 2, a multi-million-selling 2026 Godot release, kept its content as C# classes carried over from Unity and runs on a custom engine fork ("MegaDot"). — [Summary of Mega Crit's February 2026 AMA](https://slaythespire2.gg/news/mega-crit-ama-reddit-feb-2026)

### Inferences
- The simulation here is modest: tens of enemies, a 2D field lookup per mover, simple state machines, at 60 steps a second. It already runs in JavaScript on phones. Typed GDScript is slower than V8's JIT, possibly by a large factor on tight loops, so the hot paths (field sampling, route search, world generation, rollback re-simulation if used) are the candidates to watch and, if needed, move to a small GDExtension.
- World generation is the one place where JS-to-GDScript slowdown could be felt (the sewer builds sight tables between sample points). It is a one-off at load and can run on a thread.
- Mixing languages has a cost: C# cannot call a GDExtension directly without a wrapper (stated in one forum-derived summary, unverified), and AI agents do better with one language and one test runner.

### Gaps
- No rigorous, current (4.6 or 4.7) benchmark of GDScript against C# and GDExtension was found; all numbers are old or from interested parties.
- No measurement of GDScript against JavaScript (V8) for this kind of code.

## 8. Fit for AI coding agents and a code-first, test-driven workflow

### Takeaway
Godot suits an agent-driven workflow better than most engines: scenes and resources are documented plain text, the engine runs projects, scripts, imports and exports from the command line, two maintained test frameworks emit JUnit XML, and several MCP servers exist. Current frontier models write Godot 4 GDScript well when they can run the engine and read its errors; the residual failure is drifting into Godot 3 APIs.

### Cited Findings
- TSCN is "mostly human-readable and easy for version control systems to manage": a descriptor line, `ext_resource`, `sub_resource`, `node` and `connection` sections with `key = value` lines; resources carry `uid` strings so moved files keep references; comments and default-valued properties are dropped when the editor saves; a resource must appear after any internal resource it references. — [TSCN file format, Godot docs](https://docs.godotengine.org/en/stable/engine_details/file_formats/tscn.html)
- Command line: `--headless` ("Useful for servers and with --script"), `--import` ("Starts the editor, waits for any resources to be imported, and then quits"), `--export-release <preset> <path>`, `--export-debug`, `--export-pack`, `-s/--script` (scripts must "inherit from SceneTree or MainLoop"), `--check-only`, `--quit`, `--quit-after`, `--fixed-fps <fps>` ("disables real-time synchronization"), `--time-scale`, `--disable-render-loop`, `--write-movie`, `--log-file`, `--lsp-port`. — [Command line tutorial, Godot docs](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html)
- "Using the --headless command line argument is required on platforms that do not have GPU access", such as CI. — [Command line tutorial](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html)
- GUT 9.x targets Godot 4: asserts, inner test classes, doubles, stubs and spies, a command-line runner and JUnit XML export; latest 9.7.1 (July 2026); 2,785 stars. — [GUT on GitHub](https://github.com/bitwes/Gut)
- gdUnit4 supports GDScript and C#, mocking and spying, a scene runner that simulates input actions and touch and waits on signals, a command-line tool, JUnit XML and an official GitHub Action; latest v6.2.3 (1 November 2026); 1,308 stars. — [gdUnit4 on GitHub](https://github.com/godot-gdunit-labs/gdUnit4); [gdUnit4-action](https://github.com/godot-gdunit-labs/gdUnit4-action)
- CI tooling: `abarichello/godot-ci` (Docker image and templates for exporting and deploying, 1,158 stars, pushed October 2026); `chickensoft-games/setup-godot` (headless Godot on macOS, Windows and Linux runners, pushed November 2026); `firebelley/godot-export`. — [godot-ci](https://github.com/abarichello/godot-ci); [setup-godot](https://github.com/chickensoft-games/setup-godot); [godot-export](https://github.com/firebelley/godot-export)
- MCP: Coding-Solo/godot-mcp (MIT, Node, 6,711 stars, last push April 2026) lets an agent launch the editor, run a project, capture debug output, create scenes, add nodes and manage UIDs. Others include editor-embedded servers (Beckett, Godot AI, "Godot Editor MCP" on the asset library) of varying maturity. — [Coding-Solo/godot-mcp](https://github.com/Coding-Solo/godot-mcp); [Godot asset library: Godot Editor MCP](https://www.godotengine.org/asset-library/asset/5434); [Godot forum: Beckett](https://forum.godotengine.org/t/beckett-zero-sidecar-mcp-server-for-godot-4-2-the-ai-sees-and-optionally-playtests-your-game/141177)
- A vendor-run but open benchmark (Flockbay, 6 October 2026, Godot 4.7.2, 15 single-file GDScript tasks each touching an API that changed since Godot 3, checked by running headless at a fixed 60 FPS): Claude Opus 5.5, Claude Sonnet 5.5 and GPT-6.1 Sol each passed 15 of 15 first try; Claude Haiku 4.5 passed 11, then 14 after seeing Godot's error output once. Its misses were a Godot 3 call (`AnimationPlayer.add_animation`), a signal emitted twice, an untyped array returned from a typed function, and a coroutine race. The author's conclusion: the error feedback loop matters more than the first draft. — [DEV: The best LLM for Godot](https://dev.to/orellanaed/the-best-llm-for-godot-37fo)
- Attitude of the engine project to AI-written contributions: its release manager locked the C# web issue in June 2026 as "only attracting AI slop from bounty hunters". This concerns contributions to the engine, not games made with it. — [Issue 70796](https://github.com/godotengine/godot/issues/70796)
- 4.5 added custom loggers and script backtraces in release builds; 4.6 made output-panel errors link to files. — [Godot 4.5](https://godotengine.org/releases/4.5/); [Godot 4.6](https://godotengine.org/releases/4.6/)

### Inferences
- The owner's current method (drive the simulation at a fixed step from a test, assert on state, take screenshots for looks) transfers almost one to one: run a test scene headless with `--fixed-fps 60`, step and assert through GUT or gdUnit4, and capture images by running with a real renderer on the Mac (a windowed or off-screen run with `--write-movie` or viewport capture). Headless mode has no renderer, so screenshot tests cannot run with `--headless`; on CI they need a GPU or a software Vulkan or OpenGL driver. That limitation is my reading of how headless works, not a quoted statement.
- Scenes written by an agent as text are workable but fragile at the edges (resource ordering, IDs, UIDs, the editor rewriting files on save). A code-first style that builds most nodes in `_ready()` and keeps `.tscn` files small matches how the current project already builds everything in code and reduces merge conflicts between parallel agents.
- Multiplayer testing can be automated: several headless instances from the command line (one host, several clients) with netfox's built-in latency and loss simulator (v1.35.3), or two `MultiplayerAPI` branches in one process.
- Some editor-only steps remain awkward for agents: export presets and templates must be installed once, `.import` files are generated by an `--import` pass, and anything visual (materials, particles, animation trees) is faster by hand in the editor.

### Gaps
- The benchmark is small, single-file and vendor-run; there is no independent measurement of agents on a large multi-scene Godot project or on multiplayer code.
- I did not verify any MCP server by running it; star counts are not quality evidence, and the most-starred one had not been pushed since April 2026.
- Whether a screenshot test can run on GitHub's hosted macOS or Linux runners with Godot's Compatibility renderer was not confirmed.

### Inferences
- Godot's commercial credibility is no longer in doubt (multi-million sellers, console releases, studios funding the Foundation). What is unproven is exactly this project's combination: real-time 3D melee with tight timing, 4 to 5 players online. The owner would be among the first to ship that on Godot, with little prior art to copy.
- Every well-known Godot multiplayer hit uses a host or listen model over Steam with invite-only lobbies, which is the model proposed here. None of them needs prediction, because none is a twitch action game.
- Webfishing and the GodotSteam flaw are the same lesson twice: in Godot's model, RPC handlers on the host must check who sent the call.

## 10. Port effort: what translates and what must be redone

### Takeaway
About half of the 19,000 lines is gameplay data and logic that translates to GDScript nearly line for line (data tables, state machines, hooks, world-generation algorithms); the rest (renderer, figure building and posing, input, touch layout, HUD, audio, tests) is replaced by engine features or rewritten. The real new work is not the port but the things that do not exist yet: networking, authority and replication for every system that today assumes one player.

### Cited Findings
- Size by area in the current source (lines): combat, player, enemies and game state `06_game.js` 5,718; enemy behaviours `06b_ebeh.js` 1,742; world generation `03_world.js` 1,009, `03c_sewer.js` 1,589, `03b_hub.js` 422, `03d_sewerdress.js` 620, `03e_sewerview.js` 267; figures and poses `05_figures.js` 539, `05b_dbodies.js` 1,711; renderer and drawing `02_gl.js` 648, `07_render.js` 1,386, `07b_dfx.js` 389; HUD `08_hud.js` 505; touch `08b_touchlayout.js` 273, `08c_touch.js` 605; controller `08d_pad.js` 470; main and menus `09_main.js` 763; audio `04_audio.js` 314; maths `01_math.js` 144; total 19,114. There are 25 numbered test scripts. — [Local repository, src/ and tests/](file:///Users/maxlerman/Documents/Research/.research/dungeon-raze/src)
- The game keeps a single global state object `G`, one player, all damage through `hitEnemy` and `hurtPlayer`, data tables `MOVES`, `CLASSES`, `EDEF`, per-type hook tables `EBEH`, and timings in seconds. — [Project working notes, CLAUDE.md](file:///Users/maxlerman/Documents/Research/.research/dungeon-raze/CLAUDE.md)
- Engine features that replace hand-written parts: InputMap actions and SDL3 gamepad handling (4.5), a built-in VirtualJoystick node and gyro input (4.7), Control-based UI, three renderers, GPU particles, AnimationTree, physics interpolation (4.4). — [Godot 4.5](https://godotengine.org/releases/4.5/); [Godot 4.7](https://godotengine.org/releases/4.7/); [Godot 4.4](https://godotengine.org/releases/4.4/)
- Procedural meshes map to ArrayMesh or SurfaceTool. — [Procedural geometry](https://docs.godotengine.org/en/stable/tutorials/3d/procedural_geometry/index.html)
- A comparable solo port of a 3D game between engines (Unity to Godot 4) took three months and 615 hours. — [80.lv](https://80.lv/articles/this-upcoming-survival-shooter-game-switches-from-unity-to-godot)
- Slay the Spire 2's move to Godot was eased because content was already plain C# classes, not engine assets. — [Summary of Mega Crit's February 2026 AMA](https://slaythespire2.gg/news/mega-crit-ama-reddit-feb-2026)

### Inferences
- Translates directly (roughly 9,000 to 11,000 lines): `MOVES`, `CLASSES`, `EDEF`, `PURSUIT`, `SEWER`, `CROC` and the other tables become GDScript dictionaries or typed Resource classes; the player and enemy state machines, the `EBEH` hooks, pursuit and pack rules, the boss fight, the field functions (`fieldAt`, `resolve`, `los`, `route`, rock), the cave and sewer generators and the spawn rules are pure logic with no browser dependence. JavaScript closures and object literals map onto GDScript Callables and Dictionaries; the single concatenated scope maps onto a few autoloads or class_name scripts.
- Rewritten against the engine (roughly 8,000 lines, shrinking in size): the WebGL renderer, shader, effect batching and piece visibility are replaced by Godot's renderer, materials (the brick and water shader becomes a Godot shader), MeshInstance3D chunks and built-in culling; figures become node trees of primitive meshes or imported models; posing either stays procedural or moves to animations; keyboard, pad and touch code collapses into InputMap plus Control nodes, though the owner's hand-drawn touch layout would be rebuilt as a UI scene; the HUD and menus become Control scenes; audio becomes AudioStreamPlayer nodes or generators.
- Tests: the intent of the 25 scripts (hash checks of generation, placement rules over seeds, combat rule checks, boss fight walkthroughs) carries over; the harness changes from headless Chromium driving `window.DF` to GUT or gdUnit4 driving the simulation at a fixed step. They are the most valuable asset to port early, since they define correct behaviour.
- New work with no counterpart in the current code: `G` assumes one player, and enemy AI, lock-on, tokens, grabs, the boss chamber rule, rifts, mines and cave-ins all read "the player". Every one needs a decision about which player it targets and which peer decides the outcome. This redesign is engine-independent and is the bulk of the co-op effort in any engine.
- A translation by AI agents is realistic because the source and target are both plain scripts and behaviour is pinned by tests; the main hazard is silent numeric drift (integer versus float division, typed arrays), which the hash tests would catch.

### Gaps
- No measured estimate of port time for this codebase; the line split above is from file sizes, and the split into "translates" and "rewritten" is my judgement, not a measurement.
- Whether to keep primitive-built characters or commission rigged models is undecided and changes the animation work by a large factor.

## 11. Main risks, and reasons experienced developers give for and against Godot here

### Takeaway
The case for Godot is cost, licence safety, a text-based and scriptable workflow that suits agents, small builds and good enough 3D for this art style. The case against is that the netcode an online action game needs is add-on territory with thin prior art, the web and iOS-browser story is weak, C# closes off web, consoles need paid third parties, and several critical pieces (Steam, EOS, rollback) are single-maintainer community projects.

### Cited Findings
- For: MIT licence, no royalties; studios cite source access as a practical benefit ("they could dig into the engine when something misbehaved"). — [Godot console support page](https://godotengine.org/consoles/); [Summary of Mega Crit's February 2026 AMA](https://slaythespire2.gg/news/mega-crit-ama-reddit-feb-2026)
- For: Unity's 2023 runtime-fee episode moved established developers (Mega Crit, Road to Vostok) to Godot, and their games shipped and sold in 2026. — [Wikipedia: Slay the Spire 2](https://en.wikipedia.org/wiki/Slay_the_Spire_2); [Wikipedia: Road to Vostok](https://en.wikipedia.org/wiki/Road_to_Vostok)
- For: steady release cadence and corporate backing (seven platinum sponsors; W4 Games with $33 million raised). — [Godot download archive](https://godotengine.org/download/archive/); [Godot Development Fund](https://fund.godotengine.org/); [Open Source For You](https://www.opensourceforu.com/2026/08/w4-games-raises-us18-million-led-by-tencent-to-scale-godot-engine)
- For: host authority "is simpler than expected" for small co-op and "Predict only what players feel". — [Lost Rabbit Digital dev blog](https://lostrabbitdigital.pages.dev/blog/tumblefire-multiplayer-host-authority.html)
- Against: no client-side prediction, lag compensation or predicted spawning in the engine; replication nodes are considered prototype-grade by some developers. — [Rivet comparison](https://rivet.dev/blog/godot-multiplayer-compared-to-unity/)
- Against: stock Godot cannot step physics manually, which blocks physics rollback; the PR has been open since 2023. — [PR 76462](https://github.com/godotengine/godot/pull/76462); [Monke-Net README](https://github.com/grazianobolla/godot-monke-net)
- Against: lag compensation "becomes much harder with more players", and a team cut four-player co-op to two for that reason. — [Lost Rabbit Digital dev blog](https://lostrabbitdigital.pages.dev/blog/tumblefire-multiplayer-host-authority.html)
- Against: the Steam multiplayer peer had an identity flaw live from December 2025 to November 2026. — [oss-sec disclosure](https://seclists.org/oss-sec/2026/q4/518)
- Against: C# cannot target web and has no committed date. — [Issue 70796](https://github.com/godotengine/godot/issues/70796)
- Against: consoles need a paid third party and trail engine releases; C# on consoles is beta. — [W4 Consoles](https://www.w4games.com/w4consoles)
- Against: high-end 3D, asset ecosystem and built-in networking trail Unity and Unreal. — [GameFromScratch](https://gamefromscratch.com/godot-vs-unity-which-to-choose-in-2025/); [Game Design Skills](https://gamedesignskills.com/game-design/is-godot-good/)
- Against: multiplayer questions often go unanswered and documentation is scattered (2023 to 2024 assessment); the WebRTC docs page itself notes it has not been updated for the current version. — [Rivet comparison](https://rivet.dev/blog/godot-multiplayer-compared-to-unity/); [WebRTC, Godot docs](https://docs.godotengine.org/en/stable/tutorials/networking/webrtc.html)

### Inferences
- Ranked risks for this project:
  1. Netcode feel for Soulslike timing at 4 to 5 players. No engine feature and no proven Godot example covers it. Mitigation: host-authoritative enemies, each client authoritative over its own character's movement and defensive results, simple snapshot interpolation for remote entities, and no rollback unless playtests demand it. This is acceptable for invite-only co-op where cheating matters little.
  2. Dependence on community add-ons at the transport layer (GodotSteam, EOS plugin, netfox). Mitigation: put one transport abstraction in front of them, as Tumblefire did, keep ENet as a fallback, and pin versions.
  3. Losing the browser and iPhone-browser audience. A Godot web build would be GDScript only, WebGL 2 only, and unable to join Steam sessions; iOS Safari is the shakiest target. If browser play must be kept at today's quality, Godot is a step sideways or back; if it can be traded for native apps, the risk disappears.
  4. Language lock-in decided on day one: GDScript keeps every platform; C# gives speed and tooling but drops web and complicates consoles.
  5. Engine upgrades: a four-to-five-month release cadence with occasional breaking changes (for example .NET 10 and mbedTLS in 4.8) means add-ons lag; console middleware lags further.
- Reasons this project in particular fits Godot better than the generic comparison suggests: the art style needs no high-end rendering; all geometry and characters are generated in code, which Godot supports directly; gameplay collision is the game's own field, so engine physics limits barely apply; the workflow is tests and scripts, which Godot's CLI supports; the owner has a Mac, which covers iOS export; and the cost is zero until consoles.
- Reasons it fits worse: the owner wants "the correct tools" for co-op, and Godot is the engine where co-op action netcode is most do-it-yourself. Unity (Netcode for GameObjects, Fish-Net, Photon) and Unreal (built-in replication) carry more of that load; that comparison belongs to the other researchers' notes.

### Gaps
- No first-hand account from an experienced team that shipped a real-time 3D online action game on Godot and described what went wrong; the reasoning above combines smaller write-ups, forum advice and documentation.
- Community sentiment on Reddit, where most candid Godot multiplayer complaints are posted, was not read.
- I did not test any of this; every capability claim is from documentation, release notes, repository metadata or third-party write-ups.
