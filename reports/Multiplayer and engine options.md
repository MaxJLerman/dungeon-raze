# Keep the simulation, network it first

## Update of 23 November 2026: the owner's answers change the recommendation

This section was added after the report was written and supersedes the recommendation below where they differ. The rest of the report is unchanged.

The owner answered four of the open questions. Browser play does not need to be kept. Consoles are not an aim; a controller on a phone or a computer is. The game is for friends first, with strangers as the endgame. The art budget is nothing, and the owner wants to use existing character models and animation packs.

**Revised recommendation: Route B, a rebuild in Godot 4 with GDScript, after Phase 0.** This applies the report's own rule: Godot was the runner-up "if the owner decides the browser can go", and Unity displaced it mainly on console cross-play, which is no longer wanted. The reasons Route A led were reuse of the code, the browser link, agent fit and zero cost. The browser link no longer counts, and the two new requirements land on Route A's weakest points: its Steam networking binding is unproven, and it has no retargeting or animation state machine for bought or free character assets. Godot ranks second on agent fit, is free, imports GLB with retargeting onto one skeleton, and reaches Steam and native phone apps.

What does not change:

- Phase 0, the 2 to 4 week latency prototype in the existing JavaScript, still comes first. Its code is thrown away and its findings are not.
- The netcode design is the same: a player hosts and owns the world and enemies, and each player's machine owns their character.
- Route A remains the fastest way to get friends into a dungeon (4 to 6 months against 6 to 12, both estimates). It is the choice if speed matters more than where the game ends up.

What strangers as the endgame adds (to design for now and build later):

- Public lobbies do not require dedicated servers. Deep Rock Galactic lists player-hosted lobbies in a browser, and Steam lobbies carry no listed fee.
- A host or a client can cheat under this design. Comparable co-op games accept that until loot has value outside one lobby, at which point rewards need a server the owner runs. Keep the simulation able to run headless so that stays a deployment choice.
- Matchmaking that connects strangers is in scope of the UK Online Safety Act by Ofcom's guidance. Leaving text and voice chat out and using platform names keeps the duties smallest. A solicitor should confirm before public matchmaking ships.
- A run that ends when the host leaves is more costly with strangers. A rejoinable checkpoint or host migration belongs on the later list.

What a zero art budget means:

- CC0 sources cover a humanoid melee cast: Quaternius's base characters, monsters and animation libraries, and KayKit's characters and 161 clips, about 300 clips in all with no licence duties. They can be committed to the public repository.
- Mixamo is free with an Adobe account for gaps, but its raw files may not be redistributed, so they must stay out of the public repository. Its terms were read second-hand.
- Epic's own free content (Paragon characters, the Game Animation Sample) is licensed for Unreal only. It is the one asset argument for Unreal and does not outweigh that route's costs for this owner.
- No stock clip covers the crocodile's death roll or plate throw. Bosses and creatures stay procedural.
- Free clips carry their own timings, so each is time-scaled to the `MOVES` table or the table is retuned.

Still open: whether phone play is wanted as a native app. Steam's relay does not reach phones, so phone and PC players in one lobby would need a second transport (Epic Online Services, free and native only, or the owner's own relay). The choice between Godot and Unity remains the least certain call; Unity is the alternative if its deeper co-op precedent and Humanoid retargeting matter more than text-based workflow.

DungeonRaze should become a co-op game by keeping its JavaScript simulation, making that simulation multi-player and networking it as a player-hosted session in which the host owns the world and enemies and each player's own machine owns their character and judges hits on them, then replacing only the renderer with Three.js used as a library when skinned characters arrive, and reaching Steam through an Electron wrapper. This is the only route that reuses the working code (about 60% of the 19,114 lines unchanged, and all 14,723 lines of simulation and world generation already run headless in Node), keeps browser and phone play, costs nothing to run at friends scale, and keeps the agent-and-headless-test method the game was built with. The runner-up is a rebuild in Godot 4 with GDScript, which fits the same workflow and adds native builds and a paid console path, at the price of the browser audience and a 6 to 12 month port (estimate); Unity is the conventional third choice and becomes the runner-up if console cross-play and a bought-animation pipeline outweigh workflow; Unreal is the worst fit for this owner. No engine solves the two hard problems: about a dozen core functions and the 1,212-line boss assume exactly one player, and 0.2 second parry windows must survive 50 to 150 ms of latency. Both are owed on every route, so the first step on any route is the same 2 to 4 week latency prototype in the existing code (estimate), and the engine decision should wait for its result and for the owner's answers on browser play, Steam, consoles and art budget. Blender is not an alternative to any of these: it is the asset tool that feeds whichever one is chosen. All running-cost, effort and bandwidth figures below are estimates built on unmeasured assumptions, and nothing in the research was tested on a real phone, a real network or with real players.

## The engine is the smaller decision: two problems follow the game everywhere

The owner's question is framed as a choice of engine, and the research says the engine is the smaller part of the answer. Five researchers working separately on netcode, the codebase, Godot, Unity and Unreal reached the same conclusion from different directions: single-player to co-op is a redesign that the engine does not perform. The codebase audit puts it concretely. The game has one player object and no attacker or target anywhere in the damage path: `hitEnemy(e, dmg, post, o)` looks up `G.player` itself for the class bonus, backstab angle, knock direction and focus (`src/06_game.js:2488-2575`, 11 call sites), and `hurtPlayer(dmg, e, atk)` does the same for the victim (`src/06_game.js:2622-2714`, about 14 call sites). Enemies compute distance and direction to the one player once per step (`src/06_game.js:4359-4363`), attack tokens are a global cap of two (`src/06_game.js:2268-2275`), one flag says whether "the player" is in the boss chamber (`src/06_game.js:5627-5633`), a grab assumes one hold in the world (`src/06_game.js:2721-2738`), and death rebuilds every enemy (`src/06_game.js:2107-2158`). The crocodile chooses where to surface, whom to throw plates at, where the ceiling falls and when to reset from one player's position (`src/06b_ebeh.js:692-710`, `:1451`, `:1219-1220`). The auditor's judgement is that an engine's networking layer covers transport, replication and lobbies but "does not answer" who an enemy targets, how tokens, grabs, executions and the boss treat several players, or what death means in a party (researcher inference from the code).

The second problem is feel under latency. Parry windows are 0.18 to 0.28 s by class and dodge invulnerability 0.26 to 0.32 s, both judged at the instant the enemy's hit resolves (`src/06_game.js:2627-2668`). If a remote machine judges that instant, the window shrinks by roughly the round trip plus the interpolation buffer (auditor's inference). The shipped-game evidence points the same way: the two co-op action games whose players complain that dodges fail, Darktide and Lords of the Fallen, are the two where a remote authority decides whether the player was hit ([Fatshark forums](https://forums.fatsharkgames.com/t/server-authoritative-gameplay-is-terrible-and-needs-to-go/105184); [Steam discussion](https://steamcommunity.com/app/1501750/discussions/0/3934517778349929251)). These are player reports, not developer statements. Unreal, the engine with the most built-in netcode, leaves the same gap: its Gameplay Ability System does not predict damage executions or effect removal ([GASDocumentation](https://github.com/tranek/GASDocumentation)), and one developer reported root-motion melee stuttering and cancelling on clients from about 60 ms ping ([Epic forum](https://forums.unrealengine.com/t/gas-replicated-root-motion-from-montage-struggles-with-latency-and-collisions/1522235)). Godot's engine has no prediction, reconciliation or lag compensation at all ([Rivet comparison](https://rivet.dev/blog/godot-multiplayer-compared-to-unity/)).

Against those two problems, the existing code is in better shape than its single concatenated scope suggests. In an experiment outside the repository, the auditor loaded files `01_math.js` through `06b_ebeh.js` into a Node `vm` context with a four-line stub block and simulated 30 seconds of play without a single browser global being touched; a step cost 0.19 ms on the cave with 32 to 47 enemies and 0.67 ms on the sewer with 93 to 109 enemies awake near the player, a heavier load than real play (measured on Apple arm64 under Node 22). Input already flows through two functions, `held` and `hit` (`src/06_game.js:153-163`). The D enemy hooks never read `G.player` for behaviour; they read `c.p`, which `enemyUpdate` builds per enemy, so a per-enemy target flows through them with little change (inference). The class, move and enemy tables contain no functions and export as data. What the code lacks is ids on entities, an event channel for sounds and effects (about 94 sound calls and 37 spark calls sit inline in simulation code), and a per-player version of roughly a dozen functions.

Two gaps in this evidence matter. The auditor read the crocodile's 1,212 lines only in part, and the tests were not run for the audit, so their pass state is unverified. The single-player feel has also never been tuned over a long period by hand, so adding networking means tuning two things at once (auditor's stated risk).

## Host owns the world, each player owns themselves: the netcode that fits this game on any engine

### The model and why the alternatives lose

The recommended architecture is a relayed, player-hosted session. The host simulates the world, every enemy and the boss. Each client simulates its own character and is the authority on whether an enemy's attack hit, was dodged, parried or blocked. Attackers propose hits on enemies against what they see, and the host validates loosely and applies them. Everything else is drawn by interpolating snapshots. Vendor documentation supports each piece: Unity calls host architecture "essentially free", suited to fewer than 12 players, and says soft validation is "acceptable for most PvE games" ([Unity listen-server guide](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.5/manual/learn/listenserverhostarchitecture.html); [Unity latency guide](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.5/manual/learn/dealing-with-latency.html)); Unreal calls listen servers suited to casual co-op in small groups ([Unreal networking overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/networking-overview-for-unreal-engine)); Destiny shipped the split between a physics host for damage and each console owning its own movement and abilities to "feel like a single-player shooter" ([Destiny networking write-up](https://gist.github.com/nessus42/17c433143c68bc4500c5637616557e86), a fan summary of Bungie's talk). The Unity and Godot researchers arrived at the same split independently.

Lockstep and rollback are ruled out by what they demand of the code. Both need results identical "down to the bit level" on every machine ([Gaffer on Games](https://gafferongames.com/post/deterministic_lockstep/)), and JavaScript's `Math.sin`, `cos`, `pow` and `exp` are not specified exactly and have changed between engine versions ([MacWright](https://macwright.com/2020/02/14/math-keeps-changing)). The simulation calls unseeded `Math.random` at about 20 gameplay sites and runs on a variable timestep in the live loop (`src/09_main.js:336-355`). A dedicated authoritative server for everything is the fallback, not the start: it makes every player feel the round trip unless full prediction of the 690-line player state machine is built, and it is never free.

The researchers did not fully agree here, and the difference changes the work. The codebase auditor's refactor list and the browser-networking researcher's protocol both assume the classic shape, inputs up and snapshots down, with the local player predicted and reconciled; the netcode researcher recommends that the client simply own its character. This report sides with client ownership for three reasons: it preserves the parry and dodge windows at any ping, it removes the reconciliation of a large state machine, and the same `playerUpdate` code already exists to run on the client. The costs are real and accepted: any client can cheat about itself, the host can cheat about the world, and an enemy's reaction to a parry is seen by others about one round trip plus the buffer late. Unity's own Boss Room sample chose full server authority and its documentation warns that mixing client-driven players with server-driven AI "can easily have become a mess" ([Unity latency guide](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.5/manual/learn/dealing-with-latency.html)), which is why the prototype below comes before anything else. No published developer account describes victim-side parry judgement in a shipped Soulslike; the pattern is inferred from Destiny, a Risk of Rain Returns patch note and a Dark Souls 3 mod description (stated gap).

| Thing | Authority | How the others see it |
|---|---|---|
| A player's position, state machine, stamina, dodge, guard | That player's client | Interpolated from owner state sent about 30 times a second |
| Whether an enemy attack hit, was dodged, parried or blocked | The victim's client (`hurtPlayer` runs only there) | Result event to the host, relayed |
| Whether a player's attack hit an enemy | Attacker proposes; host validates loosely and applies (`hitEnemy` runs on the host) | Attacker shows it at once; others on the next snapshot |
| Enemy AI, targets, tokens, health, posture, death, boss modes and marks | Host | Snapshots 20 to 30 times a second plus reliable events for attack starts and mode changes |
| Shots | Whoever fired: host for enemy shots (each client tests its own player), the firing client for player shots | Spawn event, simulated locally by all |
| Executions and grabs | Host arbitrates the claim; the bound pair is driven by the involved player's client | Blended in over the first part of the animation |
| Rock, mines, rifts, holes | Host, as reliable ordered events | Event list, included in the join snapshot |
| World | Host's seed plus a hash check; the field data on a mismatch | Generated locally |
| Hit-stop, slow motion, shake, rumble | Local only | Not sent |
| Saves, unlocks, rewards | Each client, for itself | Not sent |

This table is the netcode researcher's design (researcher inference mapped onto the project's code). Three mechanics need specific handling. Telegraphs arrive late on a client by half the round trip plus the buffer, so a client can start a wind-up late and play it slightly faster to land the active frame at the host's time, since `wind`, `act` and `rec` are data; whether a compressed telegraph still reads is untested and is the researcher's own suggestion. Executions need a host-granted claim because nothing stops two players choosing the same staggered enemy (`src/06_game.js:2819-2831`); Halo Reach hid the same two-body mismatch with a 0.75 s visual blend ([Edgegap summary of Bungie's talk](https://edgegap.com/blog/game-backend-deep-dive-halo-reach-netcode-host-migration)). Grabs invert today's code: the victim decides whether the grab landed and drags itself, and the host moves the enemy to follow, with a timeout so a silent client cannot leave an enemy in `hold`. Hit-stop and slow motion already live in the frame loop and not in `update` (`src/09_main.js:344-351`), so making them local is a small change, but with four melee players the summed requests come to roughly 0.66 s per second if left global (auditor's arithmetic), and the feel needs retuning.

### Numbers: rates, bandwidth and what a remote player experiences

The suggested rates are a 60 Hz simulation as now, host snapshots at 20 Hz to start, client state at 30 Hz, and remote entities drawn 100 ms in the past, widening to 150 ms under loss. Fiedler's measurements put the workable interpolation delay at three send intervals on lossy links, 150 ms at 30 packets a second ([Gaffer on Games](https://gafferongames.com/post/snapshot_interpolation/)). Three researchers estimated bandwidth separately and landed within a factor of three of each other, which is as much agreement as unmeasured figures deserve.

| Estimate (source note) | Assumptions | Per client, host to client | Host upload, 4 clients |
|---|---|---|---|
| Netcode researcher | 40 enemies at about 11 bytes, 5 players at about 12 bytes, 20 Hz | about 86 kbps raw; 25 to 50 kbps with delta encoding | about 350 kbps raw; 100 to 200 kbps with deltas |
| Browser-networking researcher | 30 enemies, 5 players, 10 shots, about 600 bytes on the wire, 20 Hz | about 96 kbps | about 0.4 Mbps, about 170 MB an hour |
| Codebase auditor | 30 enemies at 20 to 30 packed bytes, 20 Hz | about 96 to 144 kbps before deltas | not given |
| Distribution researcher | 5 kB/s per link, both directions together | about 40 kbps | 72 MB an hour |

None of these was measured; the first prototype should log real snapshot sizes. Two things are solid. A naive `JSON.stringify` of the enemies would be about 660 kB/s (measured object sizes of about 1.1 kB per enemy, auditor's experiment), so a hand-written binary encoder is required. And Halo Reach fitted 16 players and over 2,000 entities in 250 kbps ([Edgegap summary](https://edgegap.com/blog/game-backend-deep-dive-halo-reach-netcode-host-migration)), so this budget is conservative. At round trip R with a 100 ms buffer, a remote player sees enemies about R/2 + 100 ms behind the host, keeps their own dodge and parry windows intact, and sees their hits confirmed after R. The latency targets are design judgement: up to about 100 ms round trip should be indistinguishable from single player, 100 to 200 ms playable with visible lateness in others, and above about 250 ms worth a warning. Bungie found gaps of up to 150 ms between a predicted action and its confirmation went unnoticed by most players ([Edgegap summary](https://edgegap.com/blog/game-backend-deep-dive-halo-reach-netcode-host-migration)).

### World sync, joining, leaving, trust and the law

Sending only the seed is safe only if generation is bit-identical everywhere. The cave's tunnel wobble uses `Math.sin` and both generators use `Math.hypot` to shape the collision field (`src/03_world.js:550-555`, `:603`), and the only check that a seed gives the same world runs in headless Chromium. iPhones play through Safari, so a party can mix JavaScript engines. One agent-built multiplayer browser game in 2026 hit exactly this: browser maths differences desynchronised it until `Math.sin` and `Math.cos` were replaced ([Simon Willison](https://simonwillison.net/2026/Oct/20/battledrones/)). The cheap design is seed plus a hash of the quantised field, water and spawns, with the host sending the grids on a mismatch; the host's spawn list is used either way because enemies are host-owned. Cross-browser equality was not tested by anyone (stated gap) and is a one-day experiment: run the existing t22 hash step in Firefox and WebKit through Playwright. On native engines the same rule holds more strongly: Unity gives no floating-point determinism across architectures under IL2CPP ([Unity Discussions](https://discussions.unity.com/t/are-floating-point-numbers-deterministic-on-the-same-architecture-il2cpp/892251)). Rock from the Sapper's cave-in and the crocodile's ceiling is five numbers applied by a deterministic repaint (`src/03_world.js:243-300`) and syncs as a reliable event.

The first version should have no host migration. When a host leaves a player-hosted game "the game ceases to exist" ([Unity listen-server guide](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@2.5/manual/learn/listenserverhostarchitecture.html)), Bungie called migration a "significant engineering undertaking" ([Edgegap summary](https://edgegap.com/blog/game-backend-deep-dive-halo-reach-netcode-host-migration)), and Photon's off-the-shelf version loses everything since the last snapshot ([Photon Fusion](https://doc.photonengine.com/fusion/current/manual/host-migration)). A gate is a short run from a shared hub, so the cheap rule is to return everyone to their own hall with what they have banked, and later to resume from the last shrine. Late joiners enter in the hall or at a rest point. Enemy scaling should follow the two documented references, which scale enemy count for everything and health only for big enemies and bosses: Risk of Rain 2 adds 0.3 to its player factor per extra player ([Risk of Rain 2 wiki](https://riskofrain2.wiki.gg/wiki/Difficulty)), and Deep Rock Galactic leaves small-enemy health alone at every party size ([Deep Rock Galactic wiki](https://deeprockgalactic.wiki.gg/wiki/Difficulty_Scaling)). No sourced description of threat tables or token schemes for comparable games was found, so targeting numbers will come from playtests (stated gap).

For trust, each client should write only its own save: the host announces facts such as "boss dead in grade D" and each client records its own clear. A host must never be able to push unlocks or a wiped save into a client, and every message should be bounds-checked. Anything that must resist tampering, such as loot traded between strangers, needs a server the owner runs; Valve's own guidance is that peers validate each other and servers are used where cheating matters ([Steamworks anti-cheat](https://partner.steamgames.com/doc/features/anticheat)). The legal surface follows the same line. Ofcom's guidance says text and voice chat and matchmaking that connects users, strangers included, bring a game under the UK Online Safety Act ([Ofcom](https://www.ofcom.org.uk/online-safety/the-online-safety-act-and-gaming-know-the-risks-know-the-rules-know-how-to-comply)), with fines up to £18m or 10% of global revenue and no small-studio exemption mentioned ([Lewis Silkin](https://www.lewissilkin.com/insights/2026/03/13/digital-commerce-creative-101-online-safety-act-navigation-for-the-video-games-industry)). Invite-only lobbies with no in-game chat and voice left to Discord are the smallest surface. The distribution researcher assumed a UK developer; whether friends-only invites are still a "user-to-user service" is a question for a solicitor, not this report.

## Seven options against the same criteria

### Blender is the asset tool on every route, not a route

Blender is where meshes, rigs and animation clips are made, cleaned and converted before any engine loads them; choosing Unity, Unreal, Godot or a web engine changes the export format and the retargeting tools, not the need for an art source (asset researcher's inference). Its built-in game engine successors are not credible bases: UPBGE ships only alpha builds for Linux and Windows ([UPBGE releases](https://github.com/UPBGE/upbge/releases)), and Armory is a small Haxe project ([Armory](https://github.com/armory3d/armory)). The current release is Blender 5.3 with 5.2 LTS supported to July 2028 ([Blender release notes](https://developer.blender.org/docs/release_notes/)). GLB is the interchange format for web engines and Godot, and FBX remains the practical one for Unity and Unreal. Blender runs headless with `-b` and `-P script.py` ([Blender manual](https://docs.blender.org/manual/en/latest/advanced/command_line/arguments.html)), so a coding agent can own the conversion scripts and test their output the way it tests the game. That is the most valuable AI use in the pipeline; AI model generators are useful for props at roughly 0.25 to 0.80 USD a model and still "hit or miss" for deforming characters by a vendor's own account ([3D AI Studio](https://www.3daistudio.com/3d-generator-ai-comparison-alternatives-guide/can-ai-generate-game-ready-3d-models)).

Four pipeline findings hold on every route. First, put every humanoid class and enemy on one skeleton, which removes run-time retargeting and lets one clip library serve all. Second, start with CC0 animation: Quaternius's Universal Animation Library 2 has 130+ clips including melee combos split into hits and recoveries ([Quaternius](https://quaternius.com/packs/universalanimationlibrary2.html)), and KayKit has 161 humanoid clips ([KayKit](https://kaylousberg.itch.io/kaykit-character-animations)). Third, keep in-place clips and let the simulation keep moving bodies from the `MOVES` table; root motion hands movement to the animation and complicates netcode. Fourth, keep the crocodile, eel, grabber and tails procedural, or give them a skinned mesh whose bones the existing pose functions drive; stock crocodiles cover walk, bite and swim but not a death roll or a plate throw, and procedural animation with "very few key frames" has shipped in respected indie games ([GDC Vault](https://www.gdcvault.com/play/1020583/Animation-Bootcamp-An-Indie-Approach)). The one real engine difference is retargeting: Unity's Humanoid Avatar ([Unity manual](https://docs.unity.com/en-us/engine/current/manual/animation-section/animation-mecanim/avatar-creationand-setup/retargeting)), Unreal's IK Retargeter ([Unreal docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/ik-rig-animation-retargeting-in-unreal-engine)) and Godot's BoneMap on import ([Godot docs](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/retargeting_3d_skeletons.html)) do it natively, while on a web engine or the custom renderer it is an offline Blender step with Auto-Rig Pro at 50 USD ([Auto-Rig Pro](https://superhivemarket.com/products/auto-rig-pro)) or the free Rokoko add-on.

Art budget comes in three tiers (asset researcher's estimates). Tier one is 0 USD: CC0 characters, clips, dungeon props and audio plus Blender. Tier two is roughly 320 to 600 USD: Auto-Rig Pro, three weapon animation packs at 15 to 50 USD each, a stock crocodile, a month or two of an AI generator, perhaps a Synty pack. Tier three is commissioning the cast, about 70,000 USD at the bottom of a vendor's published studio rates ([Pixune](https://pixune.com/blog/game-art-outsourcing-price/)); the sensible use of that tier is only what cannot be bought, such as ten boss clips at 150 to 600 USD each. One licence trap applies to this project specifically: the repository publishes through GitHub Pages, and Fab, Unity and Synty terms all forbid redistributing source assets. Fab names a private repository as the allowed way to share ([Fab licence](https://www.fab.com/eula)), and Unity says users should not be able to extract raw asset files ([Unity support](https://support.unity.com/hc/en-us/articles/34387186019988-Can-I-use-assets-from-the-Asset-Store-with-other-engines)), which sits badly with GLB files served at plain URLs. CC0 assets avoid the question. Synty's licence also forbids generative-AI use of its models ([Synty EULA](https://syntystore.com/pages/end-user-licence-agreement)).

### The comparison at a glance

| Criterion | Custom engine plus networking | Three.js as a library | Babylon.js | PlayCanvas | Godot 4 (GDScript) | Unity 6 | Unreal 5 |
|---|---|---|---|---|---|---|---|

### Keeping the custom engine and adding networking

This is the fastest route to four friends in a dungeon and the base of the recommended route. Nothing is rewritten, the tests keep running through an alias, and the same code runs as host, as client predictor of its own player and as a headless Node process. Its limit is art: the renderer has no skinning, shadows or post-processing. A dependency-free GLB loader with skinning is a few hundred lines (asset researcher's inference), so real skeletons are reachable without an engine, but each further feature is hand-built. Its other limit is platform: a web page has no console path at all (stated absence of evidence, not a sourced impossibility), and the second publishing target, the single hosted HTML page whose content policy blocks other sites, cannot do multiplayer and must have networking disabled.

### Three.js, Babylon.js or PlayCanvas

All three are actively released and permissively licensed, with WebGPU and a WebGL 2 fallback: Three.js r187 of 30 October 2026 ([three.js releases](https://github.com/mrdoob/three.js/releases)), Babylon.js 9.37.1 ([Babylon.js releases](https://github.com/BabylonJS/Babylon.js/releases)) and PlayCanvas 2.24.2 ([PlayCanvas engine](https://github.com/playcanvas/engine/releases)). None ships netcode. The game's field collision should be kept on all of them, because one function drives collision, sight, routes, shots and the camera and the same arrays run on a server.

Three.js ranks first for this codebase (web-engine researcher's inference, not a sourced verdict) because it is the only one designed to sit under someone else's game loop. The existing renderer is already a narrow interface (`R.setWorld`, `R.drawWorld`, `R.sprite`, `R.ribbon`, `R.ring`, `R.blob`, `R.nodePos`, `R.toScreen`), the existing GLSL ports nearly as it is to a `ShaderMaterial`, the piece-visibility system survives, the bundle is about 185 kB gzipped against Babylon's 1.8 MB full core, and it has about 39 times Babylon's weekly npm downloads ([Utsubo comparison](https://www.utsubo.com/blog/threejs-vs-babylonjs-vs-playcanvas-comparison)), which matters when agents write the code. Its animation mixer has crossfades and additive blending ([three.js docs](https://threejs.org/docs/pages/AnimationAction.html)) but no state machine, events or root motion, a small gap here because the simulation owns timing and position and the animation is only a view. Its risks are breaking changes every 7 to 11 weeks, agents suggesting deprecated APIs (the project publishes an [llms.txt](https://threejs.org/docs/llms.txt) to counter that), and a mid-transition from GLSL to a new shading language for WebGPU. Babylon.js is the fallback if the animation controller proves larger than expected: it has weighted and additive animation groups, frame events and two-bone IK ([Babylon.js docs](https://doc.babylonjs.com/features/featuresDeepDive/animation/advanced_animations)), clustered lighting on WebGL 2 ([Microsoft](http://blogs.windows.com/windowsdeveloper/2026/03/26/announcing-babylon-js-9-0/)) and a headless `NullEngine` ([Babylon.js docs](https://doc.babylonjs.com/setup/support/serverSide)), but it wants the game inside its scene graph and is left-handed by default against the game's right-handed conventions (the last point is background knowledge, unverified). PlayCanvas's advantages live in its cloud editor, which keeps scenes outside git, costs 15 USD a month for private projects ([PlayCanvas plans](https://playcanvas.com/plans)) and allows one agent at a time through its MCP server ([PlayCanvas editor MCP](https://github.com/playcanvas/editor-mcp-server)); a procedural, code-posed game gives a scene editor little to edit.

Beyond the browser the evidence is thin and should be read as such. One Three.js action game is documented on Steam through Electron, running on Steam Deck, and on Google Play through Capacitor ([three.js forum](https://discourse.threejs.org/t/3d-action-browser-game-made-with-three-js-savanna-sam/81902)). The steamworks.js binding exposes Steam lobbies and P2P to Electron ([steamworks.js](https://github.com/ceifa/steamworks.js)), but no shipped Electron game using Steam networking was found (stated gap). No well-known third-person action game on Steam comes from these engines, and Vampire Survivors launched in a web framework and moved to Unity after success ([Summer Engine](https://www.summerengine.com/make-great-games/threejs-game-on-steam.md), a vendor article). That precedent cuts both ways: the web stack was good enough to find the audience. On performance, 5 players and about 30 enemies at one skinned mesh each is on the order of 80 to 120 draw calls (inference), at the edge of PlayCanvas's "100-200 draw calls" guidance for low-end mobile ([PlayCanvas manual](https://developer.playcanvas.com/user-manual/optimization/guidelines/)); no measured benchmark on a named phone exists for any of the three (stated gap).

### Godot 4

Godot 4.7.2 is the stable release with 4.8 in beta ([Godot archive](https://godotengine.org/download/archive/)), MIT licensed with no fees. Its fit for this owner's method is the best of the native engines: scenes are documented plain text ([Godot docs](https://docs.godotengine.org/en/stable/engine_details/file_formats/tscn.html)), the engine runs imports, scripts, tests and exports from the command line with `--headless` and `--fixed-fps` ([Godot docs](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html)), two maintained test frameworks emit JUnit XML ([GUT](https://github.com/bitwes/Gut); [gdUnit4](https://github.com/godot-gdunit-labs/gdUnit4)), several headless processes on one machine make a co-op test, and in a small vendor-run benchmark three frontier models passed 15 of 15 Godot 4 GDScript tasks first try ([Flockbay](https://dev.to/orellanaed/the-best-llm-for-godot-37fo)). Procedural meshes from script are first-class ([Godot docs](https://docs.godotengine.org/en/stable/tutorials/3d/procedural_geometry/index.html)), and the game's own field collision sidesteps the largest limit of Godot's netcode add-ons, the lack of manual physics stepping.

The case against is that co-op action netcode is the most do-it-yourself here, although under the recommended design that matters less than it sounds, since the design uses no prediction or rollback. A listen server for 4 to 5 players is the documented default ([Godot docs](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html)). The one maintained prediction add-on, netfox, has shipped only small shooters, racers and party games ([netfox](https://github.com/foxssake/netfox)). The Steam layer is community code: GodotSteam's multiplayer peer accepted a forged server identity from December 2025 until the fix in 4.24 ([oss-sec disclosure](https://seclists.org/oss-sec/2026/q4/518); [GodotSteam](https://codeberg.org/godotsteam/godotsteam)), so host code must validate the sender of every call. One team cut four-player co-op to two because lag compensation got harder with each player ([Tumblefire dev blog](https://lostrabbitdigital.pages.dev/blog/tumblefire-multiplayer-host-authority.html)). Godot's commercial hits with online play are turn-based or slow-paced, such as Slay the Spire 2 with 3 million first-week sales ([Wikipedia](https://en.wikipedia.org/wiki/Slay_the_Spire_2)); no shipped real-time 3D melee co-op game with a netcode write-up was found (stated gap). The browser gets worse: web export is WebGL 2 only, C# cannot export to web at all, the docs warn of Safari issues ([Godot docs](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)), and users report crashes on iOS browsers ([Godot forum](https://forum.godotengine.org/t/webgl-context-loss-and-app-crash-in-godot-4-3-exported-web-on-ios-browsers/81024)). A browser build also cannot join a Steam or ENet session. Consoles go through W4 Games at 800 USD a year per platform for small studios, trailing the engine by a version ([W4 Consoles](https://www.w4games.com/w4consoles)). GDScript is the only language that keeps every platform open.

### Unity 6

Unity is the conventional choice with the deepest co-op precedent. Personal is free up to 200,000 USD of revenue with no forced splash screen, and Pro is 2,310 USD a seat a year ([Unity pricing](https://unity.com/products/pricing-updates)). Unity 6.3 is the LTS, supported to December 2027 ([Unity support](https://unity.com/releases/unity-6/support)). The recent co-op hits by tiny teams used ordinary player-hosted networking: Lethal Company on Netcode for GameObjects ([Lethal Company modding wiki](https://lethal.wiki/dev/advanced/networking)), and R.E.P.O. on Photon's oldest SDK by a team with "no prior experience with multiplayer" ([Photon blog](https://blog.photonengine.com/r-e-p-o-multiplayer-success-powered-by-photon/), a vendor case study). None had parry windows, so they prove the model and not the feel. Agent tooling changed in 2026: Unity ships a free CLI that runs tests, builds and C# in a live editor ([Unity blog](https://unity.com/blog/meet-the-unity-cli)) and an official Claude Code plugin with 29 skills ([Unity blog](https://unity.com/blog/unity-plugin-for-claude-code)), and one developer reports a 42,628-line Unity game with 589 tests built without a click in the editor ([Project Aegis devlog](https://cxyda.github.io/ProjectAegisDevLog)). The in-editor MCP server that preceded the CLI was deprecated within months in its favour ([Unity CLI docs](https://docs.unity.com/en-us/unity-cli/replace-mcp-server-unity-cli)), and the report of CLI 1.0 on 17 November 2026 comes from a single third-party article (stated gap).

The friction is structural. Scenes and prefabs are a reference graph that Unity staff tell agents not to edit as files ([Unity Discussions](https://discussions.unity.com/t/tips-and-tricks-for-using-claude-code-codex-with-the-unity-cli/1740182)); only one editor can open a project, so parallel agents need separate worktrees with separate import caches; every machine needs a licence; and in-editor multiplayer testing stops at four players ([Multiplayer Play Mode](https://docs.unity3d.com/Packages/com.unity.multiplayer.playmode@1.6/manual/index.html)), so a fifth is a built player. The platform is mid-transition: Netcode for GameObjects 3.0 in September 2026 pulled in Netcode for Entities and renamed assemblies ([NGO changelog](https://docs.unity3d.com/Packages/com.unity.netcode.gameobjects@3.2/changelog/CHANGELOG.html)), Unity 7 with a new .NET runtime is due as a preview in December 2026 ([Unity blog](https://unity.com/blog/unite-seoul-keynote-2026-recap)), and Unity closed its own server hosting on 1 April 2026 ([Unity status](https://status.unity.com/info_notices/362941)). A browser build survives, including on listed phone browsers ([Unity manual](https://docs.unity.com/en-us/engine/6000.3/manual/platform-specific/webgl/intro/browsercompatibility)), but as a multi-megabyte, single-threaded secondary target ([Unity manual](https://docs.unity.com/en-us/engine/6000.3/manual/platform-specific/webgl/intro/technical-overview)); no official size or phone load-time figure was found (stated gap). Asset Store combat kits found were single-player, so the combat core is written, not bought.

### Unreal 5

Unreal 5.8 offers the most complete built-in stack: server-authoritative replication, a predicted character controller ([Epic docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/understanding-networked-movement-in-the-character-movement-component-for-unreal-engine)), free relays and lobbies through Steam and Epic Online Services ([Epic Online Services](https://onlineservices.epicgames.com/llms.txt)), and no cost until a title grosses 1 million USD, then 5% ([VGC](https://videogameschronicle.com/news/epic-confirms-its-new-unreal-engine-pricing-keeps-its-promise-not-to-change-it-for-game-developers)). It is still the worst fit for this owner on every axis that distinguishes the options. The browser is only an experimental target in the 5.9 Preview ([Epic 5.9 preview notes](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-5-9-release-notes)). There is no Mac-to-Windows toolchain, so Steam builds need a Windows machine or cloud build ([Epic forum](https://forums.unrealengine.com/t/is-it-possible-to-build-for-windows-on-a-mac/299333), a search-result summary of older threads). Gameplay assets are binary and reached by agents only through an MCP plugin Epic labels Experimental ([Epic docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-mcp-in-unreal-editor)); in an independent test agent turns took 5 to 15 minutes and player input setup failed after 25 ([Puget Systems](https://www.pugetsystems.com/?p=48127)). Its combat tooling presumes skeletal characters with authored clips, the opposite of the game's little-art premise, and generated dynamic meshes get neither Nanite nor distance fields ([Epic docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/geometry-scripting-users-guide-in-unreal-engine)), so the engine's headline rendering gives this game little. Epic also said in June 2026 that in Unreal Engine 6 Verse largely replaces C++ ([Edge](https://knowledge.edge-online.com/p/ai-goes-native-in-unreal-engine-the-five-main-takeaways-from-state-of-unreal-2026)), so gameplay C++ written in 2027 faces a port. The closest structural analogue, Deep Rock Galactic, took five experienced developers two years to early access ([Wikipedia](https://en.wikipedia.org/wiki/Deep_Rock_Galactic)), and a solo three-player Unreal co-op action RPG took about two years of spare time ([Epic forum](https://forums.unrealengine.com/t/skylorn-bound-together-sci-fi-open-world-co-op-action-rpg/2656118)). Unreal becomes attractive only if the owner decides the game is a PC and console product with bought or commissioned character art.

## Running costs: nothing at friends scale, and two researchers' tables reconciled

Every player-hosted route costs nothing or nearly nothing to run while the game is small. Steam charges 100 USD once per app ([Steam Direct](https://partner.steamgames.com/doc/gettingstarted/appfee)) plus a 30% revenue share, and no Steamworks page lists a fee for lobbies, P2P or its relay network ([Steam Networking](https://partner.steamgames.com/doc/features/multiplayer/networking)); Valve never writes "free" on the pages read, so that rests on the absence of a listed fee (stated gap). Steam's relay serves Steam builds only, so a game that also runs in browsers needs a second transport. In browsers the cost is the relay for the minority of connections that cannot go direct. Sources put that share at 10 to 22% ([Trystero docs](https://raw.githubusercontent.com/dmotz/trystero/main/docs/troubleshooting.md); [OpenVidu](https://openvidu.io/blog/2026/06/09/turn-key-considerations/)), the hard data is from 2016 and 2017, and one WebRTC engineer disputes the commonly quoted failure figure (stated gap). With four links per lobby and 85 to 90% direct success each, a third to a half of five-player lobbies would have someone unable to join without a relay (inference assuming independent links), so a relay is effectively required. Cloudflare's is 0.05 USD per GB with the first 1,000 GB a month free ([Cloudflare Realtime pricing](https://developers.cloudflare.com/realtime/sfu/pricing/)), about an eighth of Twilio's 0.40 USD ([Twilio](https://www.twilio.com/en-us/stun-turn/pricing)).

The two cost tables in the notes differ by a factor of two to three, and the cause is assumptions, not prices. Both treat "N concurrent lobbies" as N lobbies running 24 hours a day for 730 hours, a deliberate upper bound; a game whose evening peak is N pays perhaps a third to a half.

Two reconciliations follow. For the browser relay, the truth lies between the two rows: the per-link traffic differs threefold because one researcher assumed delta-compressed snapshots and the other did not, and the free allowance was seen on one Cloudflare page and not on another. A fair reading is **0 to 5 USD a month at 10 lobbies, roughly 5 to 105 USD at 100, and 500 to 1,500 USD at 1,000**. For servers, the divergence is rooms per core. The only measurement in the notes favours the denser figure for a JavaScript server: the simulation cost 0.19 to 0.67 ms a step in Node, about 1 to 4% of one core at 60 Hz before serialisation, which is 25 to 100 rooms a core (the timing is the auditor's experiment; the rooms-per-core figure is this report's arithmetic from it). The 0.25 vCPU per room assumption is better kept for a Unity, Godot or Unreal dedicated server, where nothing was measured. Hetzner's prices are inconsistent across its own pages and its cheapest plans were marked unavailable when read (stated gap).

The wider lesson is in the comparison, not the cells: player hosting is two to four orders of magnitude cheaper than dedicated servers at every scale, and for a paid game the store's 30% dwarfs all of it. The per-session hosting market is also unstable. Hathora left game hosting in 2026 ([GamesBeat](https://gamesbeat.com/hathora-acquired-will-exit-game-infrastructure-biz-and-hand-over-customers-to-nitrado/)), hosted PartyKit shut on 23 October 2026 ([PartyKit docs](https://docs.partykit.io/)), Deno Deploy is being wound down ([Deno blog](https://deno.com/blog/cloudflare)) and Unity closed Multiplay, so a plain container that runs on any server is the portable choice. Fixed costs outside running costs are small: Apple's developer programme is 99 USD a year ([Apple](https://developer.apple.com/programs/)), Google Play 25 USD once ([Google](https://support.google.com/googleplay/android-developer/answer/6112435)), and GitHub Pages is not to be used as free hosting for a commercial business ([GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)), so a commercial browser release needs other static hosting.

## Step-by-step plans for each viable route

### Phase 0, shared by every route: prove the feel before choosing an engine

The riskiest question, whether dodge, parry, block and a grab feel like single player on a client at 100 to 300 ms, is engine-independent and cheapest to answer in the code that already exists. The netcode researcher is explicit that nothing in the literature settles it for a Soulslike with executions, grabs and terrain changes together. Phase 0 is therefore the same on every route, and its code is disposable while its findings are not.

Phase 0 totals roughly 2 to 4 weeks with agents (this report's estimate; no source). The owner's answers to the questions at the end of this report are due at the same gate.

### Route D: rebuild in Unreal 5 (viable, not recommended)

A responsible Unreal plan is mostly preconditions. Before any port: a Mac that meets Epic's recommendation of an M3 chip and 32 GB of memory, where the minimum is an M1 or M2 with 16 GB depending on rendering features ([Epic macOS requirements](https://dev.epicgames.com/documentation/en-us/unreal-engine/macos-development-requirements-for-unreal-engine)), a Windows machine or cloud builder for the Steam build, and Git LFS or Perforce. Then, after Phase 0: several months to learn the editor, the C++ gameplay framework and network programming while porting the generators to C++ on Dynamic Mesh components with a Dynamic navmesh or the game's own router; a networked vertical slice of one class, a few enemies, one generated gate and two players on the Character Movement Component (not Mover, which is Experimental) with default replication (not Iris, which is off by default) and a listen server over Steam; then animation packs, retargeting and montage authoring for every character, mostly by hand in the editor; then breadth. The Unreal researcher's planning figure is several months to the slice and **one to two years or more** to the current game's breadth with co-op, an estimate from data points that include no agent-led project. The stop condition is the slice: if agent turn times and montage authoring make iteration unworkable there, stop.

## Recommendation, runner-up and the decision gates

**Recommendation: Route A.** Run Phase 0 now. If Gate 1 passes, make the simulation multi-player and network it in JavaScript, host-owns-world and players-own-themselves, over a Cloudflare room service with WebRTC and a WebSocket fallback; put Three.js behind the existing renderer interface when the art upgrade starts; wrap for Steam with Electron when a commercial release is wanted; and use Blender headless scripts and CC0 clips on one shared skeleton for characters. The reasons are cumulative. It is the only route where the hard, engine-independent work is done once in code that already has 6,779 lines of tests around it. It is the only route that keeps a link a friend can open on a phone. It ranks first for an owner who works through agents, text and headless tests, and the strongest documented agent-built games in 2026 are on this stack, including a 55,000-line Three.js project ([Claude of Duty](https://github.com/mshumer/Claude-of-Duty)). It runs at no cost until the game has an audience. And it forecloses nothing: the data tables and about 9,800 lines of logic translate line for line to GDScript or C# later, which is what Vampire Survivors did after its web version found its audience. "Proper tools" for this game means a module build, a real test harness for several clients, a networking layer with the right authority split and a real asset pipeline. A heavier engine supplies none of the first three.

What Route A does not give must be stated as plainly. It has no console path. Its Steam story rests on one documented Three.js action game and an untested Steam networking binding. It keeps the animation state machine, retargeting and effects as the owner's code and scripts. WebRTC on real phones and carriers is untested. If any of those is disqualifying, the answer changes.

**Runner-up: Route B, Godot 4 with GDScript**, if the owner decides the browser can go and the game is a native Steam product. It is second on agent fit, free, text-based, testable with several headless processes on one Mac, and its weak netcode matters little under a design that uses no prediction. **Route C, Unity, displaces it** if console cross-play, the largest asset market and the deepest pool of shipped co-op precedent matter more than workflow and vendor risk; the choice between B and C is the least certain call in this report, and the Unity researcher would describe Unity as "a strong, conventional choice" for a Steam-first product. Route D is not recommended.

The decision points, in order, are Gate 1 (does victim-side judgement feel right under latency, and what did the owner answer below), Gate 2 (after a friends beta: is host fragility bad enough to pay for a headless host), and Gate 3 (after one skinned character on real phones: stay on Three.js, fall back to Babylon.js, or take the simulation to a native engine).

## Questions only the owner can answer

The research cannot settle the following, and several of them reorder the options. Must play from a browser link, phones included, be kept, or can it be traded for native apps and a Steam build? Is a commercial Steam release the goal, and on what horizon? Are consoles a real aim or a someday; a yes removes Route A as the final home of the game. Is the game for friends with a room code or invite, or for strangers matched online; the second brings dedicated servers, anti-cheat and the clearest Online Safety Act duties. Will rewards ever need to be trusted between strangers, as the planned loot and extraction loop might; a yes means a server the owner runs. What is the art budget, 0, a few hundred or tens of thousands of dollars, and which look: the current primitive bodies on real skeletons, CC0 low-poly characters, or stylised PBR? Is the owner willing to work in an editor GUI for animation and feel, or must everything stay text and tests? What happens when a player dies in a party: downed and revived, respawn at the shared shrine, or a wipe only when all are dead? Whose progress opens a gate for a party: the host's, any member's or each player's own? Who gets kill rewards? Is it acceptable that a run ends if the host leaves? Is in-game text or voice chat wanted, given that leaving voice to Discord avoids moderation duties? Does the single self-contained HTML page remain a release target once binary assets exist? Will the repository stay public, which decides whether paid assets can be used at all without a private store? Where is the owner based, since the compliance notes assume the UK and one open 3D generator's licence excludes the UK and EU by territory ([Hunyuan3D licence](https://raw.githubusercontent.com/Tencent-Hunyuan/Hunyuan3D-2.1/main/LICENSE))? And how much time will the owner spend playing, because every researcher found the same residue of human work on every route: playing for feel, judging screenshots and deciding scope.

## What the evidence does not cover

The limits of the research are carried here so they are not mistaken for findings. Nothing was tested on a real iPhone, a real mobile carrier or a corporate network, and whether iOS Safari keeps a data-only peer connection alive after backgrounding is unconfirmed. A hidden desktop tab's timers drop to about once a second in Chrome ([Chrome for Developers](https://developer.chrome.com/blog/timer-throttling-in-chrome-88), a 2021 article not rechecked), and whether a Web Worker escapes that is contested between sources. Every bandwidth, CPU and cost figure is an estimate. Every effort figure is a researcher's or this report's judgement; no postmortem was found of a comparable JavaScript-to-engine port, of a custom renderer moved onto a web engine, or of an agent-built online co-op action game on any engine. No developer-published account says who decides a hit in the Souls games, Monster Hunter, Deep Rock Galactic, Risk of Rain 2, Remnant 2 or Helldivers 2; several primary sources (the Valve Developer Wiki, Epic's licence and Online Services pages, Reddit, blender.org) refused automated reads, so some licence terms and tool details are second-hand, and several vendor blogs with a commercial stake are cited for prices. No measured benchmark of skinned characters on a named mid-range phone exists for the three web engines, no size or load figure for Godot or Unity web builds on phones was found, and real edit-to-result timings for Unity and Unreal on a Mac were not measured. Cross-browser equality of generated worlds was not tested. The Unity CLI 1.0 report and several 2026 roadmap items rest on single third-party articles. The audit did not read the crocodile or the sewer generator in full and did not run the tests. Console programme terms, Steam's stated price for its relay, Epic Online Services limits and the UK data protection fee amount were not confirmed.

## Conclusion

The research changes the shape of the question. The owner asked which engine makes this a proper multiplayer game; the notes show that the properness lies in three things no engine ships: a simulation in which "the player" has become "a player", an authority split that lets each machine judge its own reflexes, and a test harness that can run a host and four clients on one machine in seconds. The existing code is closer to all three than its single concatenated scope suggests, and further from them than any engine's feature list can bridge. That is why the first month of work is identical on every route and why its outcome, not an engine comparison, should decide the rest.

The second shift is that the choices are less exclusive than they look. Blender serves every route. The netcode design and the party rules are the same on every route. The data tables and the logic translate to any language, so building co-op in JavaScript first is a rehearsal for a native port and not a detour from one. The only decisions that close doors are the ones the owner alone can make: whether a link in a browser still matters, whether consoles do, and how much of the game's character should be bought, generated or kept as code.
